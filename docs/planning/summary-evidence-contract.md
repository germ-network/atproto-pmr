# Stable summary evidence for declaration records

**Status:** implementation approved by Mark on 2026-10-23; contract decisions recorded below.

## Goals

Let clients evaluate a newly delivered or changed declaration key using monitor evidence carried with the owner’s summary, while ensuring the evidence describes the exact declaration content delivered.

## Detailed scope

- In: retain first-observation time anchors for accepted declaration identities; bind those anchors to exact record/version and DID-method-specific authority/history identities; distinguish complete custody-chain evidence from a relaxed current-key cross-check seed; report observation age as a duration; carry a separate remaining server recheck TTL; pair evidence atomically with held snapshot bytes; preserve it through full and delta responses, continuation pages, and token baselines; expose stable evidence changes; define migration and unavailable behavior.
- Out: new endpoints, push behavior, handle policy, cancellation/redo of the batched currency endpoint, client trust and send policy, deployment claims, or unrelated monitor redesign.

## Acceptance

- An unchanged declaration’s first-observation time anchor survives quiet refresh, reconnect, process restart, and downtime. Successful rechecks update a separate latest-verification basis and may renew server recheck TTL; they do not reset first-observed age.
- Evidence is paired with the exact accepted record observation, never by DID alone; the binding accounts for subject DID + collection/rkey, record CID, signed commit CID and `rev`, verified signing key, and method-specific authority/history identity (which may be derivable rather than redundantly encoded).
- Commit/version first-observed history and anchor-key first-observed history remain distinct: the former binds to the declaration observation; the latter binds to the anchor and DID-method authority/history identity across commits.
- Every accepted evidence history identifies its assurance mode. The preferred mode follows DID-document authority history to the key authorized for a repository commit, then verifies the signed commit and Merkle proof for the declaration; for `did:plc`, authority history includes its verifiable PLC operation history. If that chain is missing or unavailable, a separate relaxed seed mode may use a fresh authoritative DID document/current key (fresh PLC query for `did:plc`; fresh HTTPS DID-document resolution for `did:web`), the current declaration fetched through an AppView interface that returns its DID/path/record CID, and a verified PDS proof CAR for the same declaration. Verify the commit signature under the freshly resolved current key and require exact DID/path/record-CID agreement; the PDS CAR supplies signed commit CID and `rev` because the AppView response does not establish enclosing commit identity. An AppView API that omits record CID cannot establish this cross-source binding.
- Relaxed seed evidence means the monitor independently observed a currently declared key and an AppView declaration corroborated by a PDS proof CAR signed under that key. It does not claim complete historical custody, continuous key authority, or no prior equivocation. Invalid proofs and cryptographic contradictions reject the candidate; they do not trigger downgrade to relaxed mode. AppView/PDS disagreement is a retryable observation failure, not accepted evidence. Clients decide whether to accept each assurance mode.
- First-observed age begins when the monitor first accepts the exact bound state under any permitted assurance mode. Assurance is a separate current assessment; upgrading the same bound state does not reset the age. Thus age measures retention of that state, not duration under the current assurance. A changed identity starts a new history.
- Supporting relaxed seeding for `did:web` requires first-class fresh DID document resolution and validation. Existing cached `did:web` documents treated as hints are insufficient. PLC operation-log proof does not exist for `did:web`; its current-key authority comes from DID resolution over HTTPS and the declared domain.
- A skipped/rejected replacement cannot make a retained older record appear to have evidence for the replacement.
- Changes to any stable, decision-relevant evidence state are visible in summary diffing: binding identity, assurance, availability, provenance, or persisted first-observed anchors. Elapsed time alone does not create a delta; age and remaining TTL are computed when a record is emitted.
- Full reads, deltas, continuation pages, token advancement, and persisted token baselines describe a consistent evidence/snapshot state. A CAR from observation B is never paired with metadata from observation A; the response carries the verified pair or explicit unavailable evidence.
- Evidence-binding availability, observation-age availability, and TTL availability are independent. A clock discontinuity can leave a verified binding, assurance, and provenance available while age and TTL are unavailable. Legacy/unprovable or mismatched bindings are explicitly unavailable and are never paired with the record; no unavailable value has a reason field or synthesized data.
- A token baseline created before evidence was carried requires a fresh full read. Historical age is never backfilled.
- The reviewed plan and contract types are implemented in this checkout.

## Constraints and dependencies

- Linear source of truth: GER-3081; parent GER-2994. Downstream order is GER-3081 → GER-3077 → GER-3078 → GER-3067.
- Approved delivery direction: GER-3067 decision comment `8be2836f-008b-4d12-a160-f1ad5ac012bd` chooses summary-carried monitor evidence, first-observed age, and required key/branch identity bound to the exact declaration record/version. Device download time and PDS-asserted time are not substitutes.
- Settled choices: the monitor verifies identity against the accepted record/proof at ingest; the summary carries canonical identity and provenance rather than a duplicate proof chain solely for this evidence. Ordinary client CAR/signature/proof verification remains unchanged. Keep separate commit/version and anchor-key observation histories. Use system wall-clock time, anchored once and preserved across reconnects, rechecks, restarts, and downtime. Report age as a duration, not an absolute timestamp for client clock comparison. Declaration ordering uses the signed repository commit `rev` TID, bound to its CID; declaration path `rkey` is `self`. The logical monitor ID is its hostname; client policy decides whether to trust it. Binding, age, and TTL availability are independent; no unavailable value has synthetic data or a reason field.
- Recheck TTL is separate from first-observed age and controls when the server rechecks. A successful recheck can renew TTL without resetting observation age. The server reports remaining TTL; the client subtracts request elapsed time using a local monotonic clock, caps the result with its own maximum, and counts it down. The socket delivery path avoids shared HTTP caching; any future shared-cache path must account for cache age or be disabled. Time passing alone does not create a summary delta.
- The deployment supplies system-time synchronization. NTS/Roughtime are deferred; direct protocol use in a Worker requires UDP, which the Workers runtime does not expose. While running, compare wall-clock changes with a monotonic timer; on a detected discontinuity, age and TTL are unavailable and the `onClockDiscontinuity` callback can request an immediate recheck, while the original anchor is retained. Successful content revalidation alone does not restore age or TTL. Across process restart/downtime, rely on deployment system-time synchronization; without an external trusted-time source, continuity cannot be independently proven across the gap.
- Stored evidence that does not match its CAR or summary index is unavailable and is not attached to that record. Legacy token baselines require a fresh full read; no age is backfilled.
- Existing `SnapshotEntry.observedAtMs` is overwritten on settle and quiet refresh; do not reinterpret it as first-observed history. Existing `freshAtMs` is a latest-confirmation freshness value and may inform the separate TTL basis only after the contract is verified. PLC operation annotations are not exact declaration first-observation evidence.
- `SummaryIndexEntry`, `SummaryRecord`, codecs, and diff now carry or compare this evidence. GER-2562/3033 coverage watermarks do not satisfy this contract.
- Implementation is authorized in this checkout. Release, wrapper re-pin, deployment, push, PR, and external publication remain separate actions.

## Contract decisions and recommendations

- **Identity binding:** Bind evidence to the exact declaration record/version and include required key/authority-history identity. Record identity is DID + path + record CID plus the signed commit CID and `rev`; the monitor validates the binding against accepted record/proof at ingest. The summary carries canonical identity fields and monitor provenance, not a duplicate proof chain solely for this evidence. Ordinary client CAR/signature/proof verification remains unchanged. Some identity values may be derived from the accepted CAR/proof.
- **Method-specific authority identity (settled):** For `did:plc`, bind to the verified PLC operation authorizing the signing key. For `did:web`, bind to the normalized DID-document URL, selected `#atproto` verification-method ID, and public-key fingerprint from a fresh resolution. A `did:web` binding means the key was in that currently resolved document; it does not prove continuous authority history.
- **Reappearing identity history (settled):** If the exact same authority identity disappears and later reappears, reuse its original first-observed anchor. The age means first retained observation of that identity, not uninterrupted authority; current authorization must still be verified before acceptance. A new PLC operation is a distinct identity with a distinct history.
- **Assurance mode (new design relaxation):** Prefer DID-document authority history through the key authorized for a signed repository commit, followed by commit/Merkle proof verification. When that history is missing or unavailable, allow a distinct current-key cross-check seed: fresh authoritative DID document/current signing key, current declaration fetched through the AppView, and a PDS proof CAR for the same declaration. For PLC, bind the seed to the current operation after checking its CID, `prev` link, and signature under the preceding operation's rotation key; this does not validate the full genesis-to-head history. Verify the CAR signature under the current key and require exact DID/path/record-CID agreement; use the PDS CAR's signed commit CID and `rev` for repository-version identity. Do not downgrade on invalid proof or contradiction; source disagreement is retryable, not accepted. Label assurance mode in retained evidence and let client policy decide trust. A later assurance upgrade for the same identity preserves its first-observed anchor.
- **DID methods:** For the relaxed seed path, query the current key using the DID method: fresh PLC state for `did:plc`, fresh HTTPS DID document for `did:web`. This makes `did:web` monitor support a requirement of the relaxation; serving a cached document as an unchecked hint is not enough.
- **Relaxed-seed freshness (settled):** The PLC state or `did:web` resolution, AppView declaration, and PDS proof CAR must be fresh within one bounded seed attempt. A stale cached DID document cannot establish current authority. Exact numeric freshness limits and method-specific validation settings are implementation configuration.
- **Observation scope (settled):** Retain separate commit/version and anchor-key first-observed histories. Commit/version history binds to the declaration observation and supports R83 high-water/currentness evaluation. Anchor-key history binds to the key and DID-method authority/history identity across changing commits and supports R71 anchor-history evaluation. These are separate facts because a record and its anchor can persist across changing commits.
- **Clock and age (settled):** First-observed age is anchored once using the monitor system wall clock when the exact evidence identity is first accepted under any permitted assurance mode. It persists across reconnects, rechecks, process restarts, and downtime. The server reports age as a duration; clients do not compare absolute server timestamps against local clocks. Declaration ordering uses signed repo commit `rev` (a TID), not its `rkey` (`self`); exact commits are bound by CID. The deployment supplies system-time synchronization; NTS/Roughtime are deferred for Worker deployments because they require UDP. If clock continuity is lost or a discontinuity is detected, age is unavailable, TTL is invalidated, and an immediate recheck is triggered; retain the original anchor. Rechecking content alone does not restore confidence in a suspect clock anchor.
- **Recheck TTL (settled):** Keep TTL independent from first-observed age. Its basis is latest successful verification; rechecks may renew TTL but never reset first-observed age. The server reports remaining recheck TTL. The client measures request elapsed time on a local monotonic clock, subtracts it from the reported duration, then caps it at its own maximum and counts it down locally. The socket delivery path avoids shared HTTP caching; any future shared-cache path must account for cache age or be disabled. Time passage alone does not create summary deltas; compare stable evidence state and compute age/TTL at emission.
- **Availability (semantics settled):** Binding, age, and TTL availability are independent. Legacy/unprovable/mismatched binding is unavailable with no synthetic identity, assurance, provenance, age, or TTL. Clock discontinuity may leave binding/assurance/provenance available while age and TTL are unavailable. No unavailable value has a reason field. On the wire, CBOR `null` means explicitly unavailable; an omitted field means the sender omitted or does not support it.
- **Provenance and trust (settled):** Carry the logical monitor identity as its hostname. Client policy decides whether to trust it; provenance does not itself authorize the monitor. No separate clock-sequence identity or signed-time attestation is required.
- **Hostname normalization (settled):** Encode the monitor hostname as a lowercase IDNA ASCII DNS name without a trailing dot or port, giving clients a stable provenance identity.
- **Diff state (settled):** Diff every stable, decision-relevant evidence field, including assurance and availability transitions, provenance, binding identity, and persisted anchors. Do not diff render-time age or countdown TTL.
- **Mismatch handling and old tokens (settled):** Evidence mismatched with its CAR or summary index is unavailable and is never attached to the record. Legacy rows and old token baselines have no backfilled age; a client with a baseline predating evidence must perform a fresh full read.
- **Migration boundary (settled):** The contract defines legacy evidence as unavailable with no backfill and requires a fresh full read for old token baselines. Exact storage schema versions and rollout sequencing belong to implementation planning.
- **Compatibility constraint (settled):** There are no live clients, and the live backend can restart its backfill if needed. Backward compatibility is not a design requirement for this change.
- **Package release sequence (settled):** Release `@germ-network/atproto-pmr-core` and `@germ-network/atproto-pmr-monitor-cloudflare` as `0.2.0` together, then separately re-pin and release the Germ wrapper. Current package versions are `0.1.11`; the `0.2.0` bump signals this contract change without promising backward compatibility.
- **Backend state reset (settled):** On deployment of the evidence schema, automatically initialize a dedicated evidence-refresh backfill cursor at its initial position and resume it after restarts. Sweep every currently indexed declaration and force ordinary fetch/verification; do not reset the existing missing-DIDs-only baseline backfill, since it skips rows already indexed. Preserve existing snapshots and unrelated operational state. Treat evidence-less legacy rows as unavailable until refreshed; atomically attach newly established evidence to a successfully revalidated snapshot. The sweep may be restarted and repeated safely because exact-identity anchors are idempotent. Summary tokens whose stored baseline predates evidence return a full read, so the backend need not erase all token state.
- **Consumer policy boundary:** Evidence age does not select thresholds or outcomes for R60/R71/R83. The client contract must define those rules. TIDs provide declaration ordering only; recheck/cache TTL controls refresh behavior.
